# Concerns & Technical Debt

> Generated by gsd-codebase-mapper (concerns focus) on 2026-04-13

## Summary

The codebase has undergone a significant consolidation from ~40 files to 26 files with 299 tests and 96% coverage. Most critical bugs from the original improvement prompt have been addressed. The remaining concerns are a mix of incomplete stub implementations (Neural Engine / Metal acceleration), one platform-portability footgun in the web UI, dependency version looseness, and a cluster of silent-failure patterns throughout the codebase.

## Critical Issues

### 1. Neural Engine VAE Conversion Strips bfloat16 — Incompatible with Pipeline dtype

- **Files:** `flux-krea/optimizers/neural_engine.py:227-228, 336`
- **Issue:** `compile_vae_decoder()` and `compile_text_encoder()` move components to CPU and cast to `float()` (float32) for CoreML tracing. The main pipeline runs in `bfloat16`. If a conversion succeeds and a CoreML model is returned and used, its float32 output must be cast back to bfloat16 before the rest of the pipeline consumes it. There is no cast back anywhere in the codebase. This is a latent bug that would surface only if CoreML conversion succeeds.
- **Impact:** Silent numeric type mismatch; dtype error or silent precision degradation in VAE output if CoreML path actually runs.
- **Fix approach:** After CoreML model load, wrap its forward in a casting shim that returns bfloat16, matching `self.dtype` from the pipeline.

### 2. SIGALRM Timeout Only Works on Unix Main Thread

- **Files:** `flux-krea/app.py:107-133`
- **Issue:** The generation timeout in `FluxWebApp.generate()` uses `signal.SIGALRM` and `signal.alarm()`, which are (a) Unix-only and (b) only valid on the main thread. Gradio runs callbacks in worker threads. The code wraps the call in `try/except (ValueError, AttributeError): pass`, silently disabling the timeout when it fails. The result is that on non-main-thread invocations — which is the common case in a Gradio server — there is no timeout at all. The user sees a timeout slider but the timeout does not fire.
- **Impact:** Hung generations cannot be interrupted via the UI. User-facing control is non-functional.
- **Fix approach:** Use `concurrent.futures.ThreadPoolExecutor` with a `future.result(timeout=...)` pattern, or use a `threading.Event` with periodic checking of a cancel flag inside the pipeline callback.

## Technical Debt

### 3. Metal Attention and MLP Acceleration Are TODOs — Claimed but Not Implemented

- **Files:** `flux-krea/optimizers/metal.py:135-140`
- **Issue:** Two explicit TODO comments state that Metal-accelerated attention and MLP kernels are not implemented because PyTorch MPS does not yet support custom kernels. The `MetalOptimizer.optimize_pipeline()` only performs device transfer and VAE float16 autocast — the same operations already done at STANDARD optimization level. The MAXIMUM optimization level therefore delivers no measurable benefit over STANDARD for attention and MLP (which are the dominant compute workloads).
- **Code:**
  ```python
  # TODO: Implement real Metal-accelerated attention when PyTorch MPS
  # supports custom kernels. The original monkey-patches in flux_metal_kernels.py
  # were no-ops — they wrapped the original forward without changes.

  # TODO: Implement real Metal-accelerated MLP when PyTorch MPS
  # supports custom kernels. Same issue as attention above.
  ```
- **Impact:** MAXIMUM optimization is misleadingly named. Users selecting it gain only VAE autocast, not the substantial speedup the name implies.
- **Fix approach:** Either document the limitation clearly in the UI (e.g., disable MAXIMUM or rename it in config descriptions), or implement real kernel-level improvements such as `torch.compile()` with MPS backend, which is available in PyTorch 2.x.

### 4. NeuralEngineOptimizer Is Not Wired into the Pipeline

- **Files:** `flux-krea/optimizers/__init__.py`, `flux-krea/pipeline.py:213-235`, `flux-krea/optimizers/neural_engine.py:366-417`
- **Issue:** `get_optimizer()` in `optimizers/__init__.py` instantiates a `NeuralEngineOptimizer` and returns it in the dict, but `pipeline._apply_maximum_optimizations()` only instantiates `MetalOptimizer` and `ThermalManager`. `NeuralEngineOptimizer` is never called from the pipeline. The `optimize_pipeline()` method on `NeuralEngineOptimizer` exists and attempts CoreML conversion but is never invoked during normal operation.
- **Impact:** Neural Engine optimization is dead code from the pipeline's perspective. Users cannot benefit from it even if coremltools is installed.
- **Fix approach:** In `pipeline._apply_maximum_optimizations()`, instantiate and call `NeuralEngineOptimizer.optimize_pipeline()` alongside `MetalOptimizer`. Or document explicitly that ANE acceleration requires a separate manual invocation.

### 5. CoreML Cache Is Fixed to Relative Path

- **Files:** `flux-krea/optimizers/neural_engine.py:77-80`
- **Issue:** The CoreML cache directory defaults to `"./neural_engine_cache"` — a relative path from wherever `main.py` is invoked. This works when run from the project root but breaks if invoked from another directory. There is no cleanup mechanism for stale `.mlpackage` files when the model config changes (e.g., different resolution or model ID).
- **Impact:** Stale cached CoreML models would be silently loaded when they do not match current pipeline config. Wrong latent shape would cause a runtime crash or silent wrong-output.
- **Fix approach:** Use `Path(__file__).parent / "neural_engine_cache"` for the default. Add a hash of (model_id, width, height) to the cache file name to invalidate when config changes.

### 6. sysctl Temperature Mapping Is a Linear Approximation

- **Files:** `flux-krea/optimizers/thermal.py:131-143`
- **Issue:** `_try_sysctl()` reads `machdep.xcpm.cpu_thermal_state` (an integer 0-3 thermal zone index on Intel Macs, not available on Apple Silicon) and maps it with `35.0 + (thermal_state * 5.0)`. This key does not exist on M-series chips (`sysctl` returns non-zero exit code). The method silently returns `None` on Apple Silicon, which then falls through to `_try_psutil()` and `_try_powermetrics()`. This is not a bug per se, but the comment ("no sudo needed, fastest") implies it works on the target hardware when it does not.
- **Impact:** First temperature read method always fails silently on Apple Silicon (the primary target). Minor — execution continues to psutil — but wastes a subprocess call every 2 seconds.
- **Fix approach:** Use `sysctl -n hw.perflevel0.physicalcpu` or IOKit-based thermal readings on Apple Silicon. Alternatively, check for macOS version and use `ioregsit` without sudo for real die temps on M-series.

### 7. psutil Temperature Sensor Keys Are Wrong for macOS

- **Files:** `flux-krea/optimizers/thermal.py:146-156`
- **Issue:** `_try_psutil()` searches for sensor keys `"coretemp"`, `"cpu_thermal"`, `"k10temp"`. These are Linux sensor names. On macOS, `psutil.sensors_temperatures()` is not implemented and returns an empty dict or raises `AttributeError`. The method catches this but the lookup loop always fails on macOS without logging.
- **Impact:** `_try_psutil()` is effectively a no-op on the primary target platform (macOS/Apple Silicon). Temperature monitoring falls through to `_try_powermetrics()` which requires sudo and typically fails too. The result: temperature is nearly always `None` on the target platform, and the system stays at `ThermalState.OPTIMAL` regardless of actual heat load.
- **Fix approach:** On macOS, use `subprocess.run(["ioreg", "-r", "-c", "AppleSmartBattery"])` or parse powermetrics without sudo via the `-n 1` flag (which does not require root when using `-s thermal` on recent macOS). Document that thermal management degrades gracefully to no-op.

### 8. Thermal Profile Changes Are Not Actuated on the Pipeline

- **Files:** `flux-krea/optimizers/thermal.py:94-101`, `flux-krea/pipeline.py:298-307`
- **Issue:** The `ThermalManager` fires callbacks when the performance profile changes, but in `pipeline.py` no callback is registered. `pipeline.generate()` only reads `get_current_profile().inference_steps_scale` to throttle steps. `max_cpu_threads` and `memory_fraction` changes from thermal profiles are never applied to `torch.set_num_threads()` or `torch.mps.set_per_process_memory_fraction()`. The thermal profile is partially wired: step throttling works, thread/memory changes do not.
- **Impact:** Thread count and memory fraction throttling under heat load does not occur. The most aggressive thermal response (CRITICAL: 60% GPU, 70% memory) has no mechanical effect.
- **Fix approach:** Register a callback in `pipeline._apply_maximum_optimizations()` that calls `torch.set_num_threads()` and `torch.mps.set_per_process_memory_fraction()` when the profile changes.

### 9. App Safety Mode Mutation Is Not Thread-Safe

- **Files:** `flux-krea/app.py:93-97`
- **Issue:** `FluxWebApp.generate()` mutates `self.config.safety_mode.enabled` based on the UI checkbox before acquiring any lock specific to config. The generation lock (`self._lock`) prevents concurrent generations but does not protect the config mutation from reads by other components (e.g., `ThermalManager` callbacks or `MetalOptimizer` reading config in background threads).
- **Impact:** Low probability race condition. In practice the thermal monitoring thread does not read `safety_mode`, so impact is low today. But any future code reading config from a background thread could see a half-mutated config.
- **Fix approach:** Apply safety mode by passing an override parameter to `pipeline.generate()` rather than mutating shared config state.

### 10. Profiler Stage Timing Uses Heuristic Fallbacks

- **Files:** `flux-krea/utils/profiler.py:127-151`
- **Issue:** When diffusers does not call progress callbacks at the expected boundaries, `FluxProfiler.profile_generation()` falls back to hardcoded proportions: encode=5% of total, decode=10% of total. These are documented as "empirically-observed" but are not verified against the current model version and will drift as diffusers internals change.
- **Impact:** Profiler output is silently inaccurate when callback granularity is insufficient. Users see plausible but fabricated timing breakdowns.
- **Fix approach:** Either use `torch.profiler` always (the `--torch-profile` flag), or clearly mark stage times as "estimated" in the summary output when falling back to proportions.

### 11. `_apply_env_vars()` Silently Discards Invalid Values

- **Files:** `flux-krea/config.py:236-238`
- **Issue:** When an env var exists but cannot be converted (e.g., `FLUX_GENERATION_WIDTH=abc`), the converter raises `ValueError` and the except block does `pass` with no log entry.
- **Impact:** Misconfigured environment variables are silently ignored. The user sees default behavior with no indication that their override had no effect.
- **Fix approach:** Log a warning at minimum: `logger.warning("Invalid value for %s: %r — using default", env_key, value)`.

### 12. `_apply_yaml()` Accepts Unknown Keys Without Warning

- **Files:** `flux-krea/config.py:164-182`
- **Issue:** `_apply_yaml()` iterates YAML keys and calls `hasattr(section_obj, key)` — unknown keys are silently skipped. A typo in `config.yaml` (e.g., `widht: 1024`) produces no warning and the default is used.
- **Impact:** Config file typos are invisible. Debugging takes longer than it should.
- **Fix approach:** Log a warning for any YAML key that does not match a known attribute.

## Security Concerns

### 13. `sudo powermetrics` Execution in Background Thread

- **Files:** `flux-krea/optimizers/thermal.py:159-173`
- **Issue:** `_try_powermetrics()` runs `["sudo", "/usr/bin/powermetrics", "-n", "1", "-s", "thermal"]` in a subprocess. This is called from the background thermal monitoring thread every 2 seconds if sysctl and psutil both fail (which they always do on Apple Silicon — see items 6 and 7). On systems where the user has a passwordless sudo entry for powermetrics, this fires a privileged process continuously during generation.
- **Impact:** Unintended privilege escalation in a background thread. On most systems, this will fail silently (non-zero exit code) because sudo requires a TTY. But if the user has previously typed their sudo password in the same session, the credential may be cached, causing unexpected privilege elevation.
- **Fix approach:** Remove `sudo powermetrics` from the automatic thermal loop entirely. If needed, document it as an optional manual command for debugging. The current fallback chain already correctly returns `None` and assumes OPTIMAL when temperature is unavailable.

### 14. HuggingFace Token Logged in System Info

- **Files:** `flux-krea/pipeline.py:410-411`, `flux-krea/app.py:215`
- **Issue:** `get_system_info()` and `_get_system_info_text()` surface `hf_token_set: True/False` in plaintext. This is not the token itself, but confirms presence. More importantly, the pipeline logs `"hf_token_set": get_hf_token() is not None` in structured dicts that may be serialized. The actual token is not logged, but the presence pattern suggests future maintainers may accidentally add `get_hf_token()` directly to log output.
- **Impact:** Low current risk, but establishes a pattern where the token environment is surfaced in logs and debug output.
- **Fix approach:** Keep the current masked pattern. Add a comment explicitly warning against logging `get_hf_token()` directly.

### 15. Gradio `share=True` Exposes the App Publicly

- **Files:** `flux-krea/app.py:319-336`, `flux-krea/config.py:75-77`
- **Issue:** `WebConfig.share: bool = False` is the default, but `--share` flag and the `web.share` config key exist with no authentication mechanism. If a user sets `share=True`, the Gradio tunnel is public with no access control, exposing the ability to trigger arbitrary generation workloads on the host machine.
- **Impact:** If enabled, any internet user can consume compute resources and trigger model inference. Not a concern with the default, but a footgun for users who want remote access.
- **Fix approach:** Document the risk. Consider adding a `web.auth` config option that maps to Gradio's `auth=` parameter when `share=True`.

## Performance Concerns

### 16. Benchmark Loads the Full 24GB Model

- **Files:** `flux-krea/utils/benchmark.py:41`
- **Issue:** `run_benchmark()` calls `pipeline.load()` with no config override to use a lighter optimization level. If the user runs `python main.py benchmark` with `optimization_level=maximum`, it loads the full model, applies maximum optimizations, then runs generations. There is no option to benchmark with a smaller model or mock pipeline.
- **Impact:** Running benchmarks always incurs the full model load cost (~2-5 minutes on first run). The `--quick` flag only reduces image resolution, not model weight.
- **Fix approach:** Acceptable as-is for a production benchmark tool. Consider adding a `--mock` flag for CI/testing contexts.

### 17. Neural Engine Benchmark Runs Full Inference Twice

- **Files:** `flux-krea/optimizers/neural_engine.py:446-491`
- **Issue:** `benchmark_ane_vs_mps()` runs a warm-up pass (2 steps, 256x256) then a timed pass (4 steps, 512x512). But there is no mechanism to compare against an MPS-only baseline in the same call — the acceleration ratio only becomes available if a previous MPS-only benchmark was stored in `self._benchmark_data`. Calling this once gives no ratio. The design requires calling it twice: once without ANE conversion, once with.
- **Impact:** The benchmark API is unintuitive and the `acceleration_ratio` field is `None` on first use.
- **Fix approach:** Run MPS-only first if no baseline exists, then convert and run again, returning a complete comparison.

### 18. Gallery Is Unbounded In-Memory Storage

- **Files:** `flux-krea/app.py:40, 140`
- **Issue:** `self._session_gallery: list = []` accumulates file paths for every generated image in the session. There is no limit. The gallery is stored as strings (paths) not PIL images, so memory impact is low, but the gallery is never displayed in the UI (no Gradio Gallery component renders it). It accumulates silently without purpose.
- **Impact:** Dead code accumulating state. Memory impact is negligible (strings only), but the gallery feature appears intentional and is not wired to the UI.
- **Fix approach:** Either wire the gallery to a `gr.Gallery` component in the UI, or remove `self._session_gallery` entirely.

## Dependency Risks

### 19. No Upper Bounds on Critical Dependencies

- **Files:** `flux-krea/requirements.txt`
- **Issue:** All dependency pins are lower-bound only (`>=`). Key packages with histories of breaking API changes have no upper bounds:
  - `diffusers>=0.34.0` — diffusers has historically changed `FluxPipeline` call signatures between minor versions
  - `gradio>=5.0.0` — Gradio 5.x had multiple breaking changes vs 4.x; no constraint against 6.x
  - `transformers>=4.50.0` — FLUX tokenizer and encoder depend on specific transformer versions
- **Impact:** A `pip install --upgrade` can silently break the pipeline without any dependency constraint catching it.
- **Fix approach:** Pin upper bounds on diffusers, transformers, and gradio: e.g., `diffusers>=0.34.0,<0.36.0`. Review and update bounds at deliberate upgrade points.

### 20. `tqdm` and `psutil` Are Unpinned

- **Files:** `flux-krea/requirements.txt:21, 31`
- **Issue:** `tqdm` and `psutil` have no version constraint at all (no `>=` either). This allows any version to be installed, including old versions with known bugs.
- **Fix approach:** Add minimum version pins: `tqdm>=4.66.0`, `psutil>=5.9.0`.

### 21. `coremltools>=8.0` Is Optional But Critical to ANE Path

- **Files:** `flux-krea/requirements-optional.txt`
- **Issue:** `coremltools` is in optional requirements. The `NeuralEngineOptimizer` lazy-imports it and gracefully degrades. However, `minimum_deployment_target=ct.target.macOS13` in the conversion call requires coremltools 7.0+ to have the `macOS13` target attribute. If an older coremltools (e.g., 6.x) is installed, this fails with an `AttributeError` that is caught by the broad `except Exception` and silently returns False.
- **Impact:** Users with old coremltools think ANE conversion failed due to model incompatibility when it actually failed due to API version mismatch.
- **Fix approach:** Check `ct.__version__` and require >=7.0 before attempting conversion, with a specific error message.

## Recommendations

Prioritized from highest to lowest impact:

1. **Fix SIGALRM timeout (Critical #2)** — The UI timeout is the most visible user-facing broken feature. Switch to `ThreadPoolExecutor.submit().result(timeout=...)`.

2. **Wire NeuralEngineOptimizer into pipeline (Tech Debt #4)** — The implementation is complete; it just needs to be called. Single import and call in `pipeline._apply_maximum_optimizations()`.

3. **Fix CoreML bfloat16 dtype mismatch (Critical #1)** — Low probability of triggering until CoreML conversion succeeds, but should be resolved before ANE becomes viable.

4. **Fix CoreML cache invalidation (Tech Debt #5)** — Hash model config into cache path to prevent stale model loading.

5. **Remove `sudo powermetrics` from background loop (Security #13)** — Replace with a documented comment. The function always fails silently on target hardware anyway.

6. **Log invalid env var values as warnings (Tech Debt #11)** — One-line fix, high value for debugging misconfiguration.

7. **Add upper-bound version pins (Dependency #19)** — Prevents silent breakage on upgrade. Low effort, high stability payoff.

8. **Add `max_gpu_utilization` and `memory_fraction` throttle actuation (Tech Debt #8)** — Wire thermal profile changes to `torch.set_num_threads()` and `torch.mps.set_per_process_memory_fraction()` via callback.

9. **Document MAXIMUM level limitations in UI (Tech Debt #3)** — Users should know MAXIMUM differs from STANDARD only in VAE autocast and thermal monitoring until real Metal kernels are available.

10. **Remove or wire session gallery (Performance #18)** — Small cleanup; either make the feature functional or remove dead state accumulation.
